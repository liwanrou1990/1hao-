# Arbitrum 漏块来源分析与低延迟研究 (V0.11, 二)

> 诚实前提：不通过减少必要数据验证来虚报 0 漏块。漏块如实入库并归因。

## 1. 83% 漏块的真实来源（实测，非估计）

| 量 | 实测值 | 来源 |
|----|--------|------|
| Arbitrum 出块间隔 | **~232 ms/块**（4.3 块/秒） | 连续采样 block_number |
| 公共 RPC 单次往返 RTT | 中位 **~162 ms**（135–356） | 5 次 block_number 计时 |
| Tier-1 单次扫描耗时 | **~556 ms** | 2 次批量 eth_call + 触发用 block_number |
| 理论覆盖上限 | **≈ 232/556 ≈ 42%**（实跑 ~17%） | interval/scan |

**根因**：一次扫描需约 **3 个网络往返**（触发 block_number + 买腿批量 + 卖腿批量），
每个 RTT ~162ms → 合计 ~550ms **远大于** 232ms 的出块间隔。因此每出 ~3–4 块我们才能完成 1 次扫描。
**瓶颈是到公共 RPC 的网络 RTT，不是计算**（路径计算 0.0%，见 dex-profile）。卖腿输入依赖买腿输出，
两段批量必须串行，无法在一次 RTT 内完成精确闭环。

实跑 ~17% 覆盖低于 42% 上限，是因为还叠加了轮询 block_number、rate-limit 与每轮开销。

## 2. 三类情况区分（二.3，验收报告 `dex-acceptance` 真实统计）

- **区块未观察**：扫描慢于出块而跳过的区块（主体，= missed_blocks）。**无法**在未扫描的前提下断言这些块
  有无机会——如实标注"未观察"，不臆测、不记为"无套利"。
- **已观察但池状态有滞后**：已扫描区块中，扫描期间链前进了 N 块（staleness_blocks>0），
  报价对应的是 ~N 块之前的状态（Arbitrum 实测 staleness ~2–4 块）。
- **已观察区块检出机会**：已扫描区块上 Tier-1 按安全上界标记的正毛收益数（当前真实数据恒为 0）。

验收报告新增列：`出块间隔(ms)`、`覆盖上限`，及"漏块三类归因"表，全部由持久化记录推导。

## 3. 低延迟研究（按抓手优先级）

1. **就近 / 低延迟 RPC（主要抓手）**：把 RTT 从 ~162ms 降到就近节点的 <20ms，则 3×20=60ms < 232ms →
   可做到接近每块全覆盖。这是唯一能从根本上消除 Arbitrum 漏块的手段（RTT 主导）。
   运维通过 `rpc_fallbacks` / `ARBITRUM_RPC_FALLBACK` 指向就近/付费低延迟节点即可，无需改代码。
2. **WebSocket `eth_subscribe newHeads`（次要）**：以推送取代轮询，去掉"触发用 block_number"这一个 RTT，
   扫描降到 ~2 RTT(~330ms)，上限升到 ~60%——**但仍 > 232ms，不能全覆盖**；WS 只改触发、不改两段批量 RTT。
   诚实说明：本受限网络仅放行主 HTTPS RPC，WSS 端点不可达，故 WS 触发在此环境**无法实链验证**，
   仅作为运维在 VPS 上可启用的方案记录。
3. **事件日志订阅（`Sync`/`Swap`）**：订阅池状态变更事件，仅对发生变更的池重新报价。对 WETH/USDC 这类
   近乎每块变动的活跃池收益有限；对安静交易对可省报价。
4. **单 RTT 近似（权衡，默认不启用）**：把卖腿按固定 base 名义额与买腿并入一次批量 → 1 RTT，但闭环
   变为近似（卖腿输入≠精确买腿输出）→ 需放宽候选下限以保持安全上界。会牺牲精确性，故默认保留 2 段精确批量。

## 4. 结论

- Base（~2s 出块）：3×RTT ≈ 0.5s « 2s → **实测漏块率 0.000**，已及时完整覆盖。
- Arbitrum（~0.23s 出块）：3×RTT ≈ 0.55s > 0.23s → 公共 RPC 下**物理上无法每块全覆盖**，实测漏块 ~0.83；
  **不虚报 0**。根本解是低延迟/就近 RPC（把 RTT 砍到 <20ms），WS 推送为辅。代码已就绪，端点由运维在
  VPS 提供；观察频率 ~1.2 次/秒、池状态滞后 ~2–4 块，对可行性监控足够，且全部漏块透明入库。
